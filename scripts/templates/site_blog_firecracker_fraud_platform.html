This was built as a pressure test for Torque stack orchestration, not as a small demo with one chart and a happy path. The stack starts from a remote Linux host, creates a Firecracker-backed k3s cluster, installs the data platform, exposes selected services publicly, generates payment traffic, scores fraud risk in real time, runs a batch feature job, writes durable data into AWS S3 and ClickHouse, and verifies that every major surface is alive.

The published stackfile is attached here: stack.yaml. A production-shaped package entrypoint is also attached as stack-packaged.yaml, with profile values such as values-prod.yaml. The host address from the lab run has been removed. The lab stack expects TORQUE_LAB_PUBLIC_IP for public endpoint checks and TORQUE_LAB_SSH for the SSH target.

Torque is useful when the deployment is not one tool. It is the VM fabric, the Kubernetes layer, the app, the data plane, the batch job, the observability stack, and the evidence that proves they agree.

The Shape Of The Deployment

The stack models a realistic fraud platform. A payments API accepts generated events and writes them to Redpanda and S3. Flink consumes the stream, calls a Ray Serve model for risk scoring, and writes decisions into ClickHouse. Argo launches a Spark batch job that computes aggregate features from the raw S3 objects and persists the curated result. SigNoz and ClickHouse provide the observability and analytics substrate.

The important part is not the list of products. The important part is that the products cross normal ownership boundaries. Firecracker belongs to the host. k3s belongs to the cluster. Argo, Spark, Flink, Ray, Redpanda, SigNoz, ClickHouse, and the API are Kubernetes workloads. S3 is a cloud data lake. Public access is host networking. Verification touches all of them.

Most deployment tools are strongest inside one of those boundaries. Torque is valuable when the deployment graph crosses several of them and still needs to be operated as one system.

What Torque Adds

Terraform can create infrastructure. Helm can install charts. Argo can run workflows. Spark can compute batch features. Flink can process streams. Ray can serve models and distribute Python work. SigNoz can show telemetry. None of those tools should be replaced by Torque.

Torque sits above them as the release program. It carries the ordered graph, the dependencies, the local and remote commands, the Kubernetes bootstrap, the public access mutations, the workload installation, the verification, and the run capture in one stack. That means the operator can reason about the whole delivery path instead of searching through a collection of shell history, Terraform state, Helm releases, Kubernetes objects, and dashboard screenshots.

Why This Is Different

A common failure mode for complex demos is that each tool looks correct in isolation while the whole system is fragile. The Kubernetes chart is installed, but public access was created by an untracked command. The stream job exists, but no one knows if the model endpoint was ready when the job started. The batch workflow ran once, but the S3 bucket name lives in a terminal export. The dashboard is reachable, but there is no record tying it back to the deploy.

Torque turns that into a single deployment object. Dependencies are explicit. Host-side mutations are part of the graph. Kubernetes manifests and commands are part of the graph. Verification is not a follow-up note; it is a phase that can fail the run. The SQLite capture gives the run a durable record instead of disappearing with the terminal scrollback.

That is the advantage over a pile of specialized tools. Torque does not ask Spark to be an orchestrator, Flink to be a release manager, Argo to own the host, or Terraform to understand streaming data correctness. It lets each system do its job and gives the entire release one graph and one proof trail.

Packaging It For Production

The lab version intentionally keeps everything visible, including the Firecracker host bootstrap and Python app sources mounted as ConfigMaps. The production package shape is different: a stack root, profile values, scripts, pinned chart inputs, app images, secret references, and sealed Torque evidence.

stacks/fraud-platform/stack.yaml
stacks/fraud-platform/scripts/*.sh
stacks/fraud-platform/app/*
stacks/fraud-platform/images/Dockerfile.*
stacks/fraud-platform/values/common.yaml
stacks/fraud-platform/values/lab.yaml
stacks/fraud-platform/values/stage.yaml
stacks/fraud-platform/values/prod.yaml

The profiles make environment differences explicit. lab owns the Firecracker host, NodePort DNAT, public IP checks, and event generator. stage uses an existing kubeconfig, smaller resources, real S3, and ingress. prod expects pinned images, no generator, existing cloud identity or secret:// backed secrets, stricter verification, and durable audit/export artifacts.

export TORQUE_STACK_ROOT=stacks/fraud-platform
export TORQUE_STACK_PROFILE=prod

torque stack plan --config "${TORQUE_STACK_ROOT}" --bundle dist/fraud-platform-plan.tgz
torque stack seal --config "${TORQUE_STACK_ROOT}" --profile prod --out dist/fraud-platform-prod
torque stack apply --sealed-dir dist/fraud-platform-prod \
  --capture dist/fraud-platform-prod.sqlite \
  --capture-tag env=prod \
  --capture-tag app=fraud-platform \
  --yes
torque stack audit --config "${TORQUE_STACK_ROOT}" --output html > dist/fraud-platform-audit.html
torque stack export --config "${TORQUE_STACK_ROOT}" --out dist/fraud-platform-run.tgz

The point is not to hide the complexity. It is to make the complexity reviewable, sealed, repeatable, resumable, and auditable. Local assumptions move into profile values. Raw credentials move behind workload identity or secret:// references. App code moves into digest-pinned images. Verification stays in the graph and remains the release gate.

Where This Fits In The Real World

The same pattern applies to fraud detection, marketplace event processing, IoT telemetry, personalization features, security analytics, billing pipelines, and internal AI platforms. These systems usually combine an API, a queue or log, a streaming job, a batch job, a model service, object storage, an analytical store, and observability. They also need public access rules, secrets, cloud credentials, health checks, and rollback or teardown behavior.

That kind of deployment is too wide for a single Helm release and too operational for a pure GitOps sync. It is also too interconnected to leave as a wiki page. Torque's stackfile is the contract for the whole scenario: what gets created, what depends on what, what can be resumed, and what evidence must exist before the run counts as successful.

The practical result is simple: a complex data platform becomes a repeatable release program. Engineers can still inspect each underlying tool, but the platform has one top-level object that explains how the pieces fit together.

Torque does not replace Spark, Flink, Ray, Argo, Kubernetes, or S3. It gives the deployment that combines them a graph, a memory, and a proof boundary.
Complex platforms need one release graph. Firecracker, Kubernetes, streaming, batch, ML, S3, and observability in one Torque stack.
